# Приёмка захвата J2534 — v0.3.7

Отчёт по двум разборам: `docs/09-capture-changes-spec.md` §10 и ревизия кода
v0.3.3 (P0/P1 в `universal_capture.js`, `bridge.py`, `capture.rs`), плюс
дефекты отчёта из разборов логов `2026-11-19 15:57:20`, `17:33:09` и `18:12:53`
(PCMflash + Scanmatik SM2). Форматы строк — `docs/11-capture-grammar.md`.

## Проверка живого лога «Идентификация» (19.11.2026, 17:01)

Короткая сессия 12.3 с, 52 посылки K-line (`0x8003`), Scanmatik `A62122`.
Проверял не по отчёту, а по кадрам `raw.log` — сверил каждый счётчик вручную.

| Что | Заявлено | Сверено по `raw.log` |
|---|---|---|
| TX | 52 / 4040 B | 52 строки; 14×253 + 16×5 + 17×7 + 132+149+8+6+4 = **4040** |
| RX | 104 / 365 B | 104 строки = 52 SOF (`len=0`) + 52 данных; 32×5 + 17×10 + 15+14+6 = **365** |
| `calls` | 156 | 52 `WriteMsgs` + 104 `ReadMsgs` (приложение читает по одному сообщению) |
| ошибки | 0 | ни одной настоящей; 1 `chan-miss` — отдельный счётчик `untracked_channels` (см. ниже) |
| холостые | 0 | ни одного `n_out=0`; каждый `ReadMsgs` вернул сообщение |
| шаг | 12.28 с | `started_at`→`ended_at` = 12.281 с |

Что в этом логе **не так** (и что сделано):

1. **Нет ни одной строки `PassThruConnect`.** Канал `ch=1` появился в `ioctl`
   без наблюдаемого `connect`; агент записал `J2534 chan-miss`. Хук проверен
   отдельно: тот же `universal_capture.js` на этой же `smj2534.dll` ловит
   `connect-enter` и `connect` и при `spawn`, и при позднем `attach` (пробник
   на 32-битном PowerShell, `PassThruOpen → Connect(0x8003) → Ioctl →
   Disconnect → Close`). Лог `17:33:09` это подтвердил и закрыл вопрос
   (см. §11): за сессию DLL загрузилась трижды, хуки вешались за 30–250 мс до
   первого обращения к каналу, `disconnect` на том же списке ловится — значит
   приложение `PassThruConnect` просто не зовёт, канал открывает драйвер.

2. **`Ошибок: 1` без расшифровки.** Первые 10 ошибок попадают в
   `counts.error_samples` и печатаются в `report.txt` (`ошибки (N):`) и
   `report.md` (`## Ошибки (N)`); полный список — `events.jsonl` (`kind=error`).
   С 0.3.6 `chan-miss` в `errors` не входит: там только настоящие сбои обмена.
   Регресс-тесты: `engine/tests/error_samples.rs` (оба случая).

3. **Живая сессия и импорт того же `raw.log` дают разное число событий**
   (209 против 224). Расходятся только служебные `#`-строки, которые живой
   путь кладёт в `facts`/пропускает, а импорт разбирает как `sys`/`summary`.
   TX/RX/шаги/байты совпадают до байта. Считать «события» между двумя
   представлениями одной сессии нельзя — это разные множества.

Ограничение, подтверждённое на этой DLL: у `smj2534.dll` 17 экспортов, из них
3 (ординалы 1377-1379 — J2534-2 `LogicalConnect`/`Select`/`QueueMsgs`) **без
имени**; `Module.enumerateExports()` их не отдаёт, поэтому они не хукаются и в
логе не видны. В `# hooks` считается только 14 поименованных `PassThru*`.

## Что исправлено в этой версии

| Приоритет | Дефект | Как закрыт |
|---|---|---|
| P0 | `ReadMsgs` выходил при любом `rc != 0`, теряя сообщения, которые драйвер уже отдал | ветка «пусто» срабатывает только при `n_out=0`; при `rc != 0` и `n_out > 0` сообщения читаются и пишутся с `partial=1` |
| P0 | `n_out > n_in` не ограничивался ёмкостью входа | чтение ограничено `min(n_out, n_in, 256)`, нарушение фиксируется строкой `J2534 msgs-overflow` и `contract=n_out_gt_n_in` |
| P0 | CAN: первые 4 байта `Data` выносились из `hex` и терялись при обратной сборке | `hex` = все `Data[DataSize]`, `len` = их число, идентификатор — `id=` + `idlen=` |
| P0 | `ExtraDataIndex` не читался | `xdi=` в строке сообщения, `meta.xdi` в парсере, счётчик `xdi_events` |
| P0 | SOF отбрасывал `hex` независимо от длины | SOF без данных — короткая строка; SOF с данными сохраняет и статус, и байты |
| P0 | FTDI/VCP: больше 16 КиБ за событие обрезалось молча | `chunkedLog`: `part=i/n`, явная отметка `truncated=1 len=… logged=…`, счётчик `truncated_payloads` |
| P0 | `dropped_events` считал вытеснение из сводки шага, а не потери захвата | разведены `dropped_events` (агент + мост) и `evicted_events` (сводка шага, `# session note`) |
| P0 | `flush()` на каждое событие моста | батч 32 КиБ / 20 мс с сохранением порядка (`emit` сбрасывает батч), счётчики `bridge_events/batches/backlog_max` |

| P1 | агрегат пустых опросов ключевался по `ch` и сливал разные `rc`/таймауты | ключ `module_load_id + gen + rc + timeout_ms`, в строке `mod=`/`gen=` |

| — | `adapter: null` при живой строке прошивки | `J2534 open`/`J2534 version` → `vendor/serial/firmware/dll_version/api`, работает и при импорте |
| — | `errors: 20` — это были `rx-empty` | `rx-empty` → `kind=sys`, отдельный счётчик `empty_polls` (по `n`), `errors` — только настоящие потери |
| — | `reads: []`, `filehash: []` не заполнялись | пустые поля не сериализуются; `filehash` заполняется по факту: файл, в который шёл `FILE write/close`, хэшируется (до 64 МиБ) |
| — | `events.jsonl` был 2.7× больше `raw.log` | поле `raw` (копия строки лога) больше не пишется; в JSONL остаётся только `kind=raw` |
| — | v0.3.6: «Итоги» обнулялись в bulk-сессии без шагов | объём берётся из счётчиков сессии, строка «Объём: по счётчикам сессии (шаги не распознаны)» |
| — | v0.3.6: `chan-miss` попадал в `errors` | отдельный счётчик `untracked_channels`, в отчёте «Каналов без Connect»; `errors` — только настоящие сбои |
| — | v0.3.6: протокол не был виден в отчёте | `counts.protocols` по TX, в отчёте строка «Протокол: `0x8003` (ISO 14230 KWP2000) · N из M» |
| — | v0.3.7: сеть (Winsock) считалась RX шины | `counts.net_tx/net_rx/net_bytes` отдельно, `tx/rx` — только адаптер; в отчётах строка «Сеть (не шина), байт» |

## Разбор лога «Чтение флеша» (19.11.2026, 17:33)

Сессия 4 мин 11 с: PCMflash снял дамп TC1797 MEVD17.2 (записано 4 194 304 B),
11 096 запросов `0x80` по K-line. Сверено по `raw.log`, не по отчёту.

| Что | Заявлено | Сверено по `raw.log` |
|---|---|---|
| TX | 11 096 / 132 492 B | 11 096 строк, сумма `len=` = **132 492** |
| RX | 22 192 / 2 662 699 B | 11 096 SOF (`len=0`) + 11 096 данных, сумма `len=` = **2 662 699** |
| длины тел | — | у каждой строки с телом число байт в `hex` равно `len=` (22 192 проверки, 0 расхождений) |
| `calls` | 33 288 | 11 096 `WriteMsgs` + 22 192 `ReadMsgs` |
| потери | — | `dropped_events=0 truncated_payloads=0 decode_errors=0 evicted_events=0` |
| `rc` | — | ни одного `rc != 0` во всей сессии |

Что дал этот лог:

1. **`chan-miss` — не ошибка.** За сессию `smj2534.dll` загрузилась **трижды**
   (`# hooks … load=1..3`), и на каждой загрузке первый вызов канала — `ioctl`
   без `PassThruConnect`; хуки при этом вешались за 30 мс (load 1), 145 мс
   (load 2) и 238 мс (load 3) до этого вызова, а `disconnect` на том же списке
   экспортов ловится. Вывод: приложение `PassThruConnect` не зовёт, канал
   открывает драйвер; все вызовы `rc=0`, дамп снят. Поэтому `chan-miss` больше
   не ошибка: `counts.untracked_channels`, в отчётах — «Каналов без Connect: 3».

2. **`steps: 0` — норма для bulk-обмена**, но отчёт печатал из-за этого
   «Посылок 0 / TX 0 B / RX 0 B» при 132 492 B в шапке того же файла. Теперь
   объём без шагов считается по счётчикам сессии и это названо явно.

3. **Протокол вообще не попадал в отчёт.** Он есть в каждом событии
   (`proto=0x8003`), но сводки не было — теперь есть (по TX, чтобы SOF-строки
   не удваивали счётчик).

## Разбор лога «Прошивка, две попытки» (19.11.2026, 18:12)

Сессия 47 с, 110 посылок K-line (`0x8003`), Scanmatik `A62122`, PCMflash 1.2.0.
Приложение шагов не размечает (`steps: 0`), обмен идёт двумя короткими попытками
с паузой 22.5 с между ними.

| Что | Заявлено | Сверено по `raw.log` |
|---|---|---|
| TX | 110 / 8101 B | 110 строк, сумма `len=` = **8101** |
| RX | 264 / 1706 B | 220 строк J2534 (**784 B**) + 44 строки LAN (922 B) — складывались в одно |
| длины тел | — | у всех 220 строк J2534 число байт в `hex` равно `len=` (0 расхождений) |
| `calls` | **0** | 330 вызовов (110 `WriteMsgs` + 220 `ReadMsgs`): строки `# agent-counters` в логе нет, счётчик не доехал |
| ошибки | 0 | ни одного `rc != 0`; отрицательных ответов (`7F`) нет |
| `chan-miss` | 2 | 2 — по одной на загрузку `smj2534.dll` (вторая на 22.9 с) |
| сеть | не показана | 44 события, 922 B, `10.0.0.118:54009 → 45.132.18.119:80` (проба лицензии) |

Что оказалось не так (исправлено):

1. **Сеть считалась обменом шины.** `rx=264/1706` в шапке — это 784 B адаптера
   плюс 922 B HTTP. Больше половины «RX» не имело отношения к ЭБУ. Теперь
   `counts.tx/rx/tx_bytes/rx_bytes` — только адаптер, сеть — `net_tx/net_rx/
   net_bytes` и отдельная строка отчёта.

2. **Транспорт врал: `vcp` при живом J2534.** `meta.transport` инициализируется
   догадкой «`ftd2xx` не загружен → `vcp`», а пересчитывался только в
   `api::detach_finalize`. Сессия закончилась выходом приложения — отчёт
   остался с догадкой. Теперь пересчёт в `finalize`, до записи отчёта.

3. **841 байт «принятых» из чужой памяти.** Одно событие `LAN RX len=841`
   содержало UTF-16-обрывки путей и сотни нулей: `lanSweep` брал счётчик из
   `OVERLAPPED.InternalHigh` без проверки статуса, а там осталось значение
   прошлой передачи. Теперь статус обязан быть успешным, счётчик больше буфера
   отбрасывается с строкой `LAN WARN …`.

4. **Пустая Mermaid-схема.** `flowchart TD Start → End` при `Шагов 0` — не
   информация, а заглушка. Вместо неё раздел «Обмен» и факты `# обмен …`:
   `# обмен 1: 3.64–4.11 с (0.47 с) · 52 посылок · TX 4040 B / RX 365 B ·
   0x80×49, 0x27×2, 0x10×1`, `# обмен 2: … · перед ним пауза 22.5 с`.

5. **`calls=0` при 330 вызовах.** `# agent-counters` в этом логе нет вовсе, и
   нули означали «счётчик не пришёл», а не «потерь нет». Теперь в строке
   `# counters` есть `agent_counters=0/1`, а в фактах — предупреждение, что
   `dropped/truncated = 0` читать как «потерь нет» нельзя.

Что видно по существу лога (это уже факты, не дефекты): попытка 1 — 52 посылки
за 0.47 с, попытка 2 — 58 за 2.50 с; в каждой `0x27` (SecurityAccess) с
128-байтным ключом, `0x10 0xFA` (flash-сессия), 49 кадров `0x80` по 245–251 B,
финал — `0x82` и `disconnect`. Суммарно 8 КБ TX — это не запись флеша.

Почему JSONL всё ещё больше `raw.log`: бюджет `docs/09` §8 задан для `raw.log` и
ZIP (компактный режим — ≤50 % от файла), а не для JSONL. На каждое событие в
JSONL приходится ~15 имён полей, а контракт §7 требует `api` и `hex` в открытом
виде. Убранное поле `raw` было единственным настоящим дублированием — 30 МБ из 84.
Дальнейшее сокращение возможно только сменой контейнера (бинарный/колоночный
`events.bin` или gzip-поток), это отдельная работа.

## Что осталось за стендом

| Пункт | Почему |
|---|---|
| Второй реальный драйвер (CHIPSOFT / OpenPort) | нужен адаптер и целевая программа |
| Живой `# attach: late` | проверяется одним attach к работающему PCMflash |
| Пассивные 05.00 (`dec=0`) «в бою» | на этой машине драйверов 05.00 нет |
| **Несколько источников в одной сессии** (PassThru + USBPcap) | сейчас `start_raw_usb` отказывается стартовать при активной сессии: у каждой сессии свой writer-task и свои часы. План: разрешить USBPcap-ребёнка при активном захвате, кормить его пакеты в тот же writer через `Cmd::UsbRaw`, тегировать события `source=`, а `raw_times` не привязывать к режиму сессии |
